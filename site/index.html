One Neuron, No Training

What editing an LLM’s weights directly is actually good for — and where it falls apart.

In November, Sparks of Weight-Space Programming showed a frontier LLM reading the raw weights of a neural network and writing new values into them: no optimizer, no gradient descent, just reasoning about matrices. The internet split in two within a day.

The doom campThis is the beginning of the end.

Models that can rewrite weights can rewrite themselves; recursive self-improvement just skipped a step.

The nothing-burger campThis is a nothing burger.

It’s steering and ablation in a sandbox; the headline result fixes a repetition bug that RL would fix anyway.

We spent a week running experiments on exactly this question:

  • agent sessions, 11 experiments, 9 models, from a 37k-parameter toy to Whisper and 4B chat models.
  • The editing agents are Claude Opus.
  • Then we rebuilt the useful part as a small open framework and reran it against the baseline both camps forget: ordinary fine-tuning.

Our answer: both camps are wrong, in instructive ways.

Weight editing is a patch, not a superpower. If you can say precisely what is wrong, a direct edit of a single neuron can fix a real failure in a frozen model, with fewer side effects than a prompt and often fewer than fine-tuning. But the edit doesn’t survive training that pushes against it, it only works where the model already “knows” the answer, and given enough examples, training data matches or beats it.

1Reading is real

Across every experiment, the agent correctly found what the network was doing, without being told where to look.

This is the part the “nothing burger” camp undersells. Blind sessions, given nothing but the weights and a few examples, converged on the same mechanism 3 times out of 3 (Whisper, language mixing, ResNet).

2Writing doesn’t survive training

This is the part the doom camp gets wrong. We asked the obvious next question: if an LLM edits a network and training then continues, what’s left of the edit?

The mechanism is mundane:

Gradient descent rebuildswhatever the loss wants.
AdamW movesevery weight at full speed.
Weight decay eraseswhat no gradient defends.
A dead neuronstays dead.

The result is a ratchet: the benefit of an edit fades, the damage stays. An edit lasts only if it moves the network somewhere the optimizer was going anyway. That makes it, at best, a head start.

A model that edits its own weights mid-training would be fighting its own optimizer, and the optimizer wins.

3But as a patch on a frozen model, it works

So we removed the optimizer. Most deployed models are frozen: nobody is training them while you use them. And they have specific, annoying, observable failures.

The recipe (the agents converged on it independently for Whisper; we generalised it):

  1. Find the signal. A linear probe on the model’s own activations at the decision point (“this is the bad case”). In every success, the model already knew: probe AUC ≈ .
  2. Find the write target. Force a few candidate first tokens and keep the one after which the model finishes the job by itself. “Sorry” → “…there doesn’t appear to be a widely known…”.
  3. Rewrite one neuron. The least-used neuron in one MLP layer becomes a detector:
    • it reads the probe direction;
    • it fires only above a threshold no ordinary token reaches;
    • when it fires, it pushes the logits toward the target.

4Training data still wins (or ties)

The fair competitor to an edit isn’t a prompt; it’s a small fine-tune on the same examples. So every task also gets a LoRA trained on exactly the practice prompts the gate saw, with targets the model wrote itself.

This matches the earlier ResNet experiment: there, the agents’ edit beat naive fine-tuning, but a standard method (DFR, balanced last-layer retraining with ~40 labelled photos per class) passed the bar where the edit didn’t.

5Does the patch survive more training?

Unrelated fine-tuning the patch ( → after steps); training that rewards the failure erases it within steps. Same lesson as section 2, from the other side.

6Where it doesn’t work

No signal, no gate.

Gemma caves 80% of the time when asked “Are you sure?”. But every reply, caving or not, starts with the same ritual apology, and its sense of “I was right” is weak (probe AUC ≤ 0.70). There’s nothing to route.

No failure, no gate.

Gemma-3-4B obeys injected words but almost never injected tool calls (1.7%). Nothing to fix.

Entangled behaviour.

Phi-3’s over-refusal is the same refusal direction firing more weakly. Small edits halve false refusals but cost 5–10 points of legitimate refusals. They’re still far more selective than abliteration (+16 to +33 points at matched false-refusal), but they don’t meet the bar.

Generalisation follows variety.

An injection gate fit on 3 attack goals learned “about to say BANANA42”; fit on 15 goals it blocked 43% of unseen ones.

7So who’s right?

Doom camp

Right: models really can read weights. They found every mechanism we planted or stumbled on.

Wrong: writing is a loan the optimizer collects, and a patch only works where the model already computes the right answer. That isn’t self-improvement; it’s rerouting.

Nothing-burger camp

Right: much of it is classic interpretability, steering and ablation.

Wrong: “classic” doesn’t mean useless. A single-neuron patch, found with an afternoon’s work or a blind agent session, fixed four real failures with near-zero collateral damage. It’s auditable: you can say exactly when it fires and what it writes. And it ships as numbers in a checkpoint, not a prompt that can get dropped or diluted.

What we’d actually do

  • A narrow, visible failure, a frozen model, little data: try the gate. Check the signal first; it takes minutes.
  • Plenty of examples and the ability to fine-tune: use them. Data generalises further.
  • Never expect a hand-written edit to survive training that disagrees with it.

Run your own

A task is one file: a model, an observable failure, the data to see it, and a scorer. Everything else (base outputs, probe, gate, matched random edit, LoRA baseline, guards, report) is shared.

# one 24 GB GPU, about an hour per task
pip install -r requirements.txt
python -m patchkit.run all entity     # data → base → signal → gate + random → LoRA → eval
python -m patchkit.run sweep entity   # gate vs LoRA as practice data grows
python -m patchkit.report             # results/SUMMARY.md + site/data/results.json

# any task on another model
python -m patchkit.run all entity --model Qwen/Qwen3-4B-Instruct-2507

Add a failure of your own: docs/ADDING_A_TASK.md (one file per failure) · the rules every task follows: docs/PROTOCOL.md.

The gate in 30 seconds 
read   : the probe direction d at layer L's MLP input      (gate_proj row of the least-used neuron)
fire   : only above a threshold no ordinary token reaches   (set on practice data)
write  : push the logits toward an opener after which the model finishes the job itself, e.g. "Sorry"
                                                            (down_proj column)

That’s about 3 × d_model numbers. Nothing is trained; the probe is fit on a few hundred practice prompts. Hyper-parameters (gain, g, k, margin) and the LoRA recipe are fixed across tasks and never tuned on held-out data.

Caveats

  • Thin statistics. Greedy decoding, one sample per prompt, held-out sets of a few hundred items. Effects of a few points are noise.
  • Rough scoring. It’s regex-based and spot-checked by reading, with no human or LLM judge.
  • Small models. 1B–4B models, one per task, plus one transfer run.
  • No adaptive attacker against the injection gate.
  • One agent model for the editing sessions.
